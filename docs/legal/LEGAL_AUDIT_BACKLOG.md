# RoScope 法務・セキュリティ監査バックログ

最終更新: 2026-07-18

対象: `writing-board-next` の全機能

対象時点の提供形態: 無償のテスト運用・実利用者ゼロ

判定: **実ユーザーへの提供開始は No-Go。少なくとも「Gate A」を完了するまで、実在する相談援助対象者・患者・利用者の情報を入力しないこと。**

> この文書は、コードと公開資料に基づく実装・運用課題の台帳であり、弁護士による正式な法律意見ではない。特に電気通信事業法、通信の秘密、契約条項、要配慮個人情報の受入可否は、提供主体・利用団体・運用実態によって結論が変わるため、専門家確認を完了条件に含める。

## 1. Claude がこの文書を使うときのルール

1. 着手前に `CLAUDE.md` と `docs/HANDOFF.md` を全文読む。
2. 一度に全課題を実装しない。ユーザーから指定された課題ID単位で、現状を再確認して着手する。
3. `要方針決定` または `要専門家確認` の課題は、利用者への説明や法的評価をClaudeだけで確定しない。選択肢と影響を提示し、決定後に実装する。
4. Server Action・DB・Storage・APIを変更する場合は、リポジトリの `/feature`、`/lessons`、必要に応じて `/mobile` を読み、`npm run check:tenant` を実行する。
5. DB変更は `supabase/migrations/` に記録し、セキュリティ仕様変更は `docs/SECURITY.md` と本台帳を同時に更新する。
6. 法務文言を変更するときは、実装と文言を同じ課題で整合させる。実態と規約・プライバシーポリシーの片方だけを直して完了扱いにしない。
7. 課題を完了したら、各課題の `状態` を `DONE (YYYY-MM-DD)` にし、実施内容・検証結果・残余リスクを追記する。

## 2. 優先度とリリースゲート

- `P0`: 実利用開始前のブロッカー。悪用または機微情報の公開につながり得る。
- `P1`: 実利用開始または対象機能の本運用前に解消・決定が必要。
- `P2`: 早期改善。直ちに提供停止までは求めないが、運用開始後の放置は不可。
- `条件付き`: 現在は機能がないため非該当。機能追加前に必ず再監査する。

リスク点は `発生可能性 1〜5 × 影響 1〜5` の暫定FMEA値であり、法的責任の確率を示すものではない。

| Gate A: 実ユーザー導入 | 初期管理者、公開Storage、削除整合、要配慮情報の入力制限、凍結、RLS fail-close、最低限のプライバシー表示・事故連絡体制 | LGL-001〜006、LGL-009、LGL-010、LGL-014 |

## 5. 課題詳細

### LGL-001: 初期管理者登録のサーバー側トークン検証

- 状態: `OPEN`
- 事実: UIは `verifySetupToken()` を実行するが、`registerUser()` は未認証時に `isInitialSetup=true` と数値の `organizationKey` があれば受け付け、既存ユーザーが0人かだけを確認してadminを作成する。
- 証拠: `app/(auth)/user/register/page.tsx:33,92-94`、`actions/admin.ts:311-365`、`lib/session.ts:129-138`
- リスク: 未完成組織または組織キーを推測された場合の初期管理者乗っ取り。並行リクエストによる二重初期登録も競合し得る。
- 必須対応:
  1. `registerUser()` 自身がセットアップトークンを受け取り、署名・用途・期限・organizationKey一致を検証する。
  2. 「既存ユーザー0人の確認」とadmin作成をDBトランザクションまたは一意制約付きRPCで原子的に行う。
  3. ワンタイム性を持たせ、成功後のリプレイを拒否する。
- 完了条件: トークンなし・改ざん・期限切れ・別組織キー・同時2リクエストのテストが全て拒否され、正常な1件だけがadminになる。

### LGL-002: 公開Storageの非公開化

- 状態: `OPEN`
- 事実: `images`、`videos`、`avatars` は公開バケットで、`getPublicMediaUrl()` が認証不要のpublic URLを生成する。福祉業務の投稿に人物・書類・対象者情報が混入するとURL保有者が取得できる。
- 証拠: `lib/storage.ts:1-3`、`actions/profile.ts:75`、`app/(dashboard)/components/PostAttachments.tsx:27-38`、`.agents/skills/context/SKILL.md` のStorage定義
- 必須対応:
  1. 投稿画像・動画はprivate bucketへ移し、組織・投稿・閲覧権限を検証して短時間署名URLを発行する。
  2. アバターも個人情報としてprivate化するか、公開範囲と本人同意を明確化する。
  3. 既存public URLの棚卸し、移行、無効化を行う。
- 完了条件: 未認証、他組織、URL履歴からのアクセスが失敗し、自組織の認可済み利用者だけが期限内に取得できる。

### LGL-003: 削除と証拠保全の整合

- 状態: `OPEN`
- 事実:
  - `deletePost()` は `writing_data` だけを削除し、Storage実体の削除を行わない。
  - `post_attachments`、既読、リアクション、返信のFK・cascade設計とStorage削除が一つの処理として保証されていない。
  - `dm_pairs.user_a/user_b` は `user_info` の削除に `ON DELETE CASCADE` で、片方の退会により相手方メッセージと報告済み証拠まで消える。
  - アカウント削除後も、投稿者名・ログ・バックアップ等にどの情報が残るかが一覧化されていない。
- 証拠: `actions/posts.ts:221-286`、`supabase/schema.sql:1432-1468,1592-1612`、`supabase/migrations/20260711_direct_messages.sql:11-35`、`app/privacy/page.tsx:107-116`
- 必須対応:
  1. データ資産ごとに `即時削除 / 匿名化して保持 / 法的保全 / バックアップから期限消去` を決める。
  2. 投稿削除をDB関連行とStorage実体の双方で失敗回復可能にする。
  3. DMは相手方の記録と報告証拠を消さない匿名化方式へ変更し、legal hold中は削除しない。
  4. UI文言、規約、プライバシーポリシーを実装に合わせる。
- 完了条件: 投稿・アカウント・団体削除の統合テストと、Storage孤児検出があり、残存データが保存期間表と一致する。

### LGL-004: 要配慮個人情報の入力・通知制御

- 状態: `OPEN`
- 事実: 利用規約は相談援助対象者の秘密を「必要最小限・特定されない形」と案内するだけで、投稿・添付・DM画面の強い警告、入力制限、管理者設定がない。投稿Pushは先頭80字、DM Pushは60字をロック画面へ表示し得る。
- 証拠: `app/terms/page.tsx:49-61`、`actions/posts.ts:125-128`、`app/api/posts/create/route.ts:107-110`、`actions/social.ts:65-70,181-186`、`actions/messages.ts:175-178`
- 必須対応:
  1. テスト期間中は「患者・利用者・相談援助対象者を特定できる情報、病歴、障害、介護記録を入力しない」を明示する。
  2. 投稿・添付・DMの入力直前に目立つ警告を設け、初回だけでなく継続表示または組織設定で強制する。
  3. Push本文を既定で非表示にし、少なくともDM・添付投稿は内容を出さない。
  4. 将来受け入れる場合は、利用目的・取得根拠・権限・監査・暗号化・委託契約・事故対応を厚労省ガイドラインと整合させて再設計する。
- 完了条件: 375px画面とPush実機で警告・非表示を確認し、利用団体向け文書にも入力禁止範囲が一致している。

### LGL-005: 凍結済みアカウントの既存セッション無効化

- 状態: `OPEN`
- 事実: ログイン時は `is_active` を確認するが、毎リクエストの `getSession()` は `is_active` をselect・判定しない。凍結済みでもCookie期限まで利用できる。
- 証拠: `lib/session.ts:61-100`、`actions/auth.ts` のログイン照合、`docs/SECURITY.md:19`
- 必須対応: `is_active` を毎回照合してfalseならnullを返し、可能ならセッション世代または失効時刻で即時失効する。ドキュメントの「凍結」仕様も実態に合わせる。
- 完了条件: ログイン済みユーザーを管理画面で凍結した直後、次のリクエストとServer Actionが拒否される。

### LGL-006: RLSのfail-close化

- 状態: `OPEN`
- 事実: `SUPABASE_JWT_SECRET` が未設定の場合、エラーを出すだけでservice roleへフォールバックし、RLS層を無効化したまま動作する。
- 証拠: `lib/supabase/server.ts:54-61,92-97`、`docs/HANDOFF.md` のISO27001残課題
- 必須対応: production/preview相当環境では必須環境変数不足を起動・build・health checkで失敗させる。開発時フォールバックが必要なら明示フラグと強い警告に限定する。
- 完了条件: secretを外した本番相当テストがfail-closeし、CIまたは起動診断で検知できる。

### LGL-007: DM報告時点のスナップショット化

- 状態: `OPEN`
- 事実: 管理者画面は `disclosed_at` があるペアについて、時刻条件なしで全メッセージを取得する。このため報告後に送られた将来の通信も継続して閲覧できる。
- 証拠: `app/(dashboard)/messages/reported/page.tsx:16-50`、`actions/messages.ts:214-218`
- 必須対応:
  1. 開示対象を報告時刻以前に固定するか、報告時点のmessage ID上限を記録する。
  2. 追加開示は当事者による別操作にする。
  3. 管理者画面に開示範囲・報告者・時刻を表示し、監査ログへ範囲を記録する。
- 完了条件: 報告後に送信したメッセージが既存報告から見えず、追加開示なしでは取得できない。

### LGL-008: 電気通信事業法・通信の秘密

- 状態: `OPEN / 要専門家確認`
- 事実: 1対1DMは他人の依頼で隔地者間の通信を媒介する機能である。現在は無償テストだが、複数団体への反復継続提供・将来の事業化により届出要否が変わる。届出不要の場合でも通信の秘密に関する評価は別途必要。
- 証拠: `actions/messages.ts`、`app/(dashboard)/messages/**`、`supabase/migrations/20260711_direct_messages.sql`
- 確認事項:
  1. 現在の提供主体、提供範囲、営利意思、継続性で届出が必要か。
  2. 当事者一方の操作で双方の全会話を管理者へ開示する設計が妥当か。
  3. 運営保守アクセス、バックアップ、事故調査、ログ保存の許容範囲。
  4. 将来の有償化・対象団体追加時に再判定するトリガー。
- 完了条件: 所管の総合通信局または電気通信分野の弁護士への相談記録と結論が残り、必要なら届出・規程・実装が完了している。

### LGL-009: プライバシーポリシーと委託先表示

- 状態: `OPEN / 要方針決定`
- 不足・不整合:
  - 運営者の法的名称、住所、代表者、問い合わせ先、苦情窓口がない。
  - 利用団体が管理主体、運営者が「委託に準じる」とするが、責任分担と委託契約の有無が曖昧。
  - 「Supabase/Vercelが保管データを独自目的で取り扱うことはありません」は各社DPAより広すぎる断定。
  - Google、Meta以外にUnison Plaza iframe、Push配信、SMTP事業者等の外部送信・委託先が一覧化されていない。
- 証拠: `app/privacy/page.tsx:35-40,76-93`、`app/(dashboard)/expenses/page.tsx:19-23,40-46`、`app/(dashboard)/schedule/UnisonPlazaAvailability.tsx:12,65-70`
- 必須対応: データマップを作成し、管理主体、委託先、送信項目、目的、送信先、保存地、問い合わせを実態どおり記載する。DPA適用プラン・契約者名も確認する。
- 完了条件: 運営者情報と連絡先が確定し、全外部送信先がコード棚卸しと一致する。利用団体との個人データ取扱条項がある。

### LGL-010: 保存期間・削除・同意証跡

- 状態: `OPEN / 要方針決定`
- 事実: DB14日バックアップ以外に、投稿、DM、アカウント、監査ログ、ログイン履歴、Push購読、Instagramキャッシュ、Storageの保存期間が定義されていない。同意チェックはあるが日時・規約版を記録しない。
