# セキュリティ管理策マッピング（ISO/IEC 27001:2022 準拠）

RoScope（writing-board-next）の技術的・運用的セキュリティ管理策を、ISO/IEC 27001:2022 附属書A の管理策に対応付けた文書。

> **注意:** ISO27001 は組織の情報セキュリティマネジメントシステム（ISMS）の規格であり、認証取得にはこの文書に加えて組織側の運用（リスクアセスメント、教育、内部監査、マネジメントレビュー等）が必要。本書は「アプリケーションが提供する技術的管理策」と「運用側で実施すべき事項」を区別して記載する。

---

## 1. アクセス制御（A.5.15 / A.5.18 / A.8.2 / A.8.3）

### 実装済み
| 管理策 | 実装 | 場所 |
|---|---|---|
| 認証必須化 | 全ページを `middleware.ts` で JWT 検証。未認証は `/login` へ | `middleware.ts` |
| ロールベースアクセス制御 | `admin` / `leader` / `member` の3ロール。管理操作は Server Action 冒頭でロール検証 | `actions/admin.ts` |
| 特権の制限（A.8.2） | リーダーは自部署のみ操作可・admin昇格不可。管理者も自分自身の削除・凍結は不可 | `actions/admin.ts` |
| テナント分離 | 全DBクエリに `organization_key` フィルタ（RLS未使用のためアプリ層が防衛線） | 全 actions / pages |
| セッション管理 | JWT 8時間有効・httpOnly・secure・sameSite=lax。ユーザー削除で即時無効化（毎リクエストDB照合） | `lib/session.ts` |
| アカウント凍結 | `is_active=false` でログイン拒否。管理画面から凍結/解除 | `actions/auth.ts` / `actions/admin.ts` |

### 運用側で実施すべき事項
- 退職・異動時のアカウント削除/凍結手順の文書化と、四半期ごとのアクセス権レビュー（A.5.18）
- 管理者アカウントを複数名に付与（単一管理者のパスワード忘れ・退職リスク対策）

## 2. 認証情報の管理（A.5.16 / A.5.17）

### 実装済み
| 管理策 | 実装 | 場所 |
|---|---|---|
| パスワードハッシュ化 | bcrypt（コスト10）。平文保存なし | `actions/auth.ts` 他 |
| パスワードポリシー | 組織ごとに最低文字数（8〜32）・有効期限（90/180/365日/無期限）を設定可能 | `password_policy` テーブル / 管理画面 |
| 初回・リセット時の強制変更 | `must_change_password` フラグでログイン後に変更画面へ強制遷移 | `actions/auth.ts` |
| パスワードリセット | 管理者が仮パスワードを発行 → 本人が初回ログインで変更（メール基盤不要のクローズド運用） | `resetUserPassword` |
| 同一パスワード再利用拒否 | 現行と同じパスワードへの変更を拒否 | `changePassword` |
| ブルートフォース対策 | ログイン試行を IP+団体ID 単位で 15分10回 に制限 | `actions/auth.ts` |

### 既知の制約・残課題
- レート制限はプロセス内メモリ実装のため、複数インスタンス構成では Upstash Redis 等への移行が必要（コード内コメントに明記済み）
- パスワード履歴（過去N世代の再利用禁止）は未実装

## 3. ログ取得・監視（A.8.15 / A.8.16）

### 実装済み
| 管理策 | 実装 | 場所 |
|---|---|---|
| ログイン履歴 | 成功ログイン（ユーザー・日時・IP）を記録、管理画面で直近50件閲覧 | `login_history` テーブル |
| 監査ログ | ログイン失敗（理由付き）・パスワード変更/リセット・ユーザー作成/更新/削除・凍結/解除・団体パス変更・ポリシー変更を記録。管理画面で閲覧 | `audit_logs` テーブル / `lib/audit.ts` |
| ログの改ざん防止 | アプリからは INSERT のみ（更新・削除のUIなし）。DB直接アクセスは service role key 保持者に限定 | — |

### 運用側で実施すべき事項
- 監査ログの定期レビュー（月次推奨）と保持期間ポリシーの策定
- Supabase / Vercel のプラットフォームログ（インフラ層）の保持設定確認

## 4. 通信・データ保護（A.8.24 / A.8.12 / A.5.33）

### 実装済み
| 管理策 | 実装 | 場所 |
|---|---|---|
| 転送時暗号化 | 全通信 HTTPS（Vercel）。HSTS（2年・preload）強制 | `next.config.ts` |
| Content-Security-Policy | default-src 'self'。接続先は Supabase のみ、埋め込みは許可リスト方式 | `next.config.ts` |
| クリックジャッキング対策 | `X-Frame-Options: DENY` + `frame-ancestors 'none'` | `next.config.ts` |
| その他ヘッダー | nosniff / Referrer-Policy / Permissions-Policy | `next.config.ts` |
| 機密ファイルの保護 | PDF は非公開バケット + 60秒署名付きURL。パスの組織プレフィックス検証 | `getPdfSignedUrl` |
| 保存時暗号化 | Supabase（PostgreSQL）のディスク暗号化に依拠 | プラットフォーム |

### 運用側で実施すべき事項
- バックアップ: Supabase の自動バックアップ設定（Pro プランで日次・PITR）の有効化確認（A.8.13）
- `JWT_SECRET` / `SUPABASE_SERVICE_ROLE_KEY` / `VAPID_PRIVATE_KEY` / `INTERNAL_SECRET` の定期ローテーション手順の策定（A.5.17）

## 5. 開発セキュリティ（A.8.25 – A.8.29）

### 実装済み
- 入力値検証: 長さ制限・正規表現・NFKC正規化・HTMLタグ除去・PDFマジックバイト検証
- SQLインジェクション対策: Supabase クライアント（パラメータ化クエリ）のみ使用
- 秘密情報の分離: `.env*` は gitignore。環境変数は Vercel 側で管理
- セキュアコーディング規約: `CLAUDE.md` + `.claude/skills/lessons` に実バグ由来のルールを整備
- 未認証セットアップ経路の悪用対策: 組織の既存ユーザー数チェック

### 運用側で実施すべき事項
- 依存パッケージの脆弱性監視（`npm audit` を CI に組み込む、または GitHub Dependabot 有効化）
- 本番デプロイ前のレビュー手順（現状は単独開発のため、変更履歴＝gitログで代替）

## 6. インシデント対応（A.5.24 – A.5.28）

### アプリが提供する手段
- アカウント凍結（即時のアクセス遮断）
- 監査ログ・ログイン履歴による影響範囲調査
- ユーザー削除によるセッション即時無効化

### 運用側で実施すべき事項
- インシデント対応手順書（検知 → 凍結 → 調査 → 報告）の策定
- 連絡体制（管理者・利用団体への通知経路）の明文化

## 7. 残課題サマリー（優先度順）

1. **RLS（Row Level Security）ポリシーの有効化** — 現状 service role でバイパスされており、アプリ層のフィルタ漏れが即データ漏洩につながる。多層防御として RLS ポリシー定義を推奨
2. **レート制限の永続化** — Upstash Redis 等への移行（スケールアウト時必須）
3. **パスワード履歴** — 過去パスワードの再利用禁止
4. **依存関係の脆弱性スキャン自動化** — Dependabot / npm audit の CI 組み込み
5. **バックアップ・リストア演習** — 年1回の復旧テスト
